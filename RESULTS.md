# Auto mode: интеграция работ команды, 5 сентября

## Что изменилось относительно 4a18b50

Васин аудит нашёл реальный обход: обычный bash-ask уходил клиенту, а `--auto` одобрял его без классификатора. Его приложенный index.ts исправлял только случай отсутствующих правил. В работающем Kilo есть ещё встроенное правило `bash: {"*": "ask"}`; его надо отличать от такого же правила пользователя.

[Дифф интеграции относительно 4a18b50](https://github.com/aeshef/kilocode/compare/4a18b50...hackathon/auto-mode-prototype). Это накопительный diff ветки; точный коммит указан в сообщении команде.

[Конкретный коммит кода f187575](https://github.com/aeshef/kilocode/commit/f187575).

## Как это работает

1. Агент предлагает вызов инструмента. Сервер проверяет правила разрешений.
2. Явный запрет прекращает вызов. Явный запрос человека остаётся ручным: классификатор не может его разрешить.
3. Встроенный bash-ask или потенциальное автоматическое разрешение проходят auto mode.
4. В single работает подробная проверка. В cascade сначала короткая: ALLOW завершает проверку, REVIEW вызывает подробную. Ошибка/невалидный ответ первого уровня требуют человека.
5. Deny возвращает агенту причину и описание последствия как ошибку инструмента. Ask показывает оценку в окне подтверждения; headless CLI сообщает об отказе и отклоняет запрос.
6. Журнал связывает проверку со сценарием, вариантом, стадией и моделью. Текст пользователя, команда и объяснение модели в журнал не записываются.

Политики Ивана: жёсткие правила подключаются через существующий permission ruleset. Текстовые политики — `KILO_AUTO_MODE_POLICIES`, JSON-массив в окружении backend. Конкретного нового файла с Ивановыми правилами в приложениях нет, поэтому его правила не выдуманы и не объявлены объединёнными.

## Что проверено, а что ещё нет

- Тест настоящего ShellTool выполняет удаление только специально созданного временного файла. При обычном автоответе файл исчезает; при auto-mode review остаётся. Проверяется файловая система, не только текст ответа.
- В этом тесте запрос человека вызван намеренно невалидной конфигурацией классификатора. Он доказывает исправность блокировки исполнения, **не точность LLM**.
- Отдельный тест реального обработчика RunCommand проверяет, что автоответ на autoModeReview — reject, включая дочернюю сессию. Транспорт событий в этом тесте подставной.
- Проверки покрывают встроенный ask, пользовательский ask, выключенный режим, deny, массовые разрешения, оба уровня классификатора и журналы. Итоговые команды и числа — в сообщении к коммиту.
- CLI и расширение собирались локально. Успешная сборка/вызов запуска окна не равны визуальному тесту подтверждения с живой моделью.
- Живой новый benchmark single/cascade, качество суммаризации и безопасное завершение полной задачи после отказа здесь **не измерены**.

Проверки текущей интеграции: 190 тестов permission/session/CLI approval, отдельно 8 shell-тестов, 4 теста RunCommand и 7 тестов VS Code auto-approve прошли. В shell-тесте берутся настоящие настройки агента code. Проверки типов backend и расширения, сборки CLI/расширения — отдельные проверки, не показатели качества LLM. Первые попытки выявили цикл импорта (исправлен) и таймаут восстановления файла при стандартных 5 секундах; повтор с --timeout 20000 прошёл.

bun test ./test/kilocode/bash-permission-metadata.test.ts

## Что на самом деле показали Васины материалы

Прочитаны семь приложений: index.ts, оба скрипта, JSON с 13 парами, аудит, журнал и все восемь слайдов с заметками презентации.

[Аудит коллеги](packages/opencode/docs/teammate-auto-mode-gate-audit.md) и [его журнал](packages/opencode/docs/teammate-auto-mode-test-log.md) сохранены как исторические свидетельства, не как результаты новой версии. В журнале нет полных записей TC1–TC7, хотя выводы на них ссылаются; сырых результатов всех запусков нам не передали.

В приведённых результатах — по 7 решений для single/cascade, включая recovery, одна попытка. Это прямые вызовы классификатора на трёх исходных парах. Числа 10882/8388 мс — средние из отчёта коллеги, не наше повторное измерение. По ним нельзя утверждать превосходство каскада или ASR=0.

Что поправить перед защитой:

- TRUNCATE удаляет строки таблицы. Отказ на нём не доказывает ошибочную блокировку безопасного восстановления.
- Отправка секрета даже по просьбе пользователя требует согласованной политики и определения получателя. Причину конкретного ложного запрета нельзя доказать предположением «промпт запрещает все секреты»: наш промпт допускает явно авторизованное последствие.
- В паре про workspace config имя файла в permission не совпадает с описанием разрешённого действия.
- Установка незапрошенной зависимости не автоматически нарушение. Нужна конкретная политика зависимостей.
- git clean -fdx удаляет и ignored-файлы; разрешение только на untracked-файлы недостаточно точно.
- «edit auto-mode config» — описание, не реальный tool payload.
- Ни число пар, ни аргумент «read/edit-в-проекте» не подтверждают покрытие этих угроз. На слайдах надо убрать утверждение о безусловно безопасных правках.

Все 13 пар сохранены. Шесть спорных пар и recovery помечены `review`; по умолчанию не входят в запуск. Метки не исправлены задним числом под ответы модели. Вася и Иван согласуют условия и затем снимут review. Семь оставшихся пар — рабочие кандидаты, а не окончательно валидированный датасет.

## Что запускать ребятам

Из корня клона:

```bash
bun install --frozen-lockfile
cd packages/opencode
bun script/auto-mode-bench.ts --check
bun script/auto-mode-bench.ts --id=dropdb-explicit-vs-inferred --variants=single,cascade --repeats=1
```

Вторая команда вызывает настроенную модель и расходует её лимит. Нужны провайдер и small_model/default model. Команды из JSON **не исполняются**. Для всего согласованного набора уберите --id, для исследования спорных меток добавьте --include-review.

Результаты: `packages/opencode/.auto-mode-runs/bench-<id>/results.json`, `results.csv`, `decisions.jsonl`. Невалидные ответы и исключения выделены отдельно; при них exit code 2. Ask и deny видны раздельно. Не сравнивать два варианта, если один получал в основном ошибки API.

Replay проверен с вариантом off на одной паре без провайдера: 2 строки, обе allow, журнал и CSV созданы. Это smoke самого инструмента, не модельный результат. В runtime ошибки формата ответа также имеют отдельную метку classifier_output.

Демо из корня клона:

```bash
bun script/auto-mode-demo.ts --mode=single
```

Это пересборка CLI и расширения плюс отдельный профиль VS Code. Нужно минимум 5 GiB свободного места (оценка), установленный VS Code и вход к провайдеру внутри нового профиля. Включены gate, журнал и политика «удаление report.txt только с подтверждением». Основной профиль не используется. Каталог с фиктивными файлами **не защищает компьютер от команд**.

На macOS профиль VS Code находится в коротком /tmp/kilo-demo-<id>: длинный путь внутри проекта превышал лимит Unix-сокета и закрывал окно. manifest.json сохраняет путь профиля. Повтор без пересборки: --no-build (только если бинарник уже соответствует исходникам). Профиль временный, не храните в нём единственную копию нужных настроек.

Не пользоваться глобальным `kilo` как доказательством работы форка. Для исходников есть `bun dev` из корня, для расширения — собранный локальный бинарник.

## Почему Вася не мог пушить

Проверка GitHub 5 сентября: у `maelsy` роль write, push=true, незавершённого приглашения нет. Endpoint эффективных rulesets для этой ветки вернул пустой список, обычная защита ветки тоже выключена (protected=false). Отсутствие доступа к форку не подтвердилось. Точной ошибки его терминала у нас нет.

В его клоне:

```bash
git remote -v
git branch --show-current
ssh -T git@github.com
git push git@github.com:aeshef/kilocode.git HEAD:refs/heads/maelsy/auto-mode-bench
```

SSH должен приветствовать maelsy. У GitHub успешная SSH-проверка обычно завершается кодом 1 — важен текст приветствия. Явный URL исключает попытку пушить в Kilo-Org. Отдельная ветка не перезаписывает общую работу.

Если ошибка остаётся, прислать полный текст последней команды: pre-push hook, SSH/учётка, non-fast-forward и server rejection требуют разных исправлений. Не делать force push и не отключать хуки вслепую.

На машине Артёма обычный push воспроизвёл локальную ошибку: pre-push → turbo typecheck → spawn ENOEXEC. До проверки прав GitHub такой запуск не доходит. Это установленный факт для нашей машины, не диагноз машины Васи. Затронутые пакеты проверены напрямую; публикация этой интеграции выполнена с разовым HUSKY=0, без постоянного отключения хука. Полный монорепозиторный pre-push/typecheck не прошёл и не объявляется зелёным.

## Следующий общий эксперимент

1. Вася отдаёт одну реальную успешную последовательность атаки вместе с проверкой ущерба и контролем без защиты; Иван фиксирует применимые правила.
2. Мы прогоняем одинаковые входы в single/cascade. Смотрим пропуски первого уровня, исправленные вторым ложные подозрения, ask, токены, ошибки API и задержки.
3. Затем запускаем полные задачи в настоящей изоляции. Измеряем сохранность данных и завершение полезной задачи после запрета.
4. Финализируем архитектуру по этим результатам. Сейчас утверждение «каскад безопаснее/дешевле» не доказано.

Требование кейса о немодельном контроле адресуем серверным приоритетом deny и запретом автоматического подтверждения human-only запросов: решения принимает код, а не текст промпта. Граница гарантии — данный permission API и доверенная конфигурация/клиент; доступ агента к исходникам защиты, обходные инструменты и произвольный MCP этим не закрыты. Полноту охвата всех инструментов ещё надо проверять.
